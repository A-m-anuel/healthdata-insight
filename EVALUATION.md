# Evaluation

This document reports a reproducible evaluation of HealthData Insight on **1,180 synthetic patients** generated by
Synthea. Every number comes from an actual run.
- Generated results: [`evaluation/results/results.md`](evaluation/results/results.md) and
  [`results.json`](evaluation/results/results.json).
- Run log: [`run.log`](evaluation/results/run.log).
- A few before/after figures for fixes made during the evaluation are measurements from development runs; they are
  marked as such.

> The project uses **synthetic data only** and is a **prototype**. These results describe behaviour on Synthea
> output under controlled conditions. They are not evidence of clinical validity, HIPAA compliance, or fitness for
> production use. See [LIMITATIONS.md](LIMITATIONS.md).

### Why batches

The pipeline holds the whole dataset in memory (see E5/E6). On the evaluation machine about 4 GB of memory was
free, so the accuracy and privacy experiments processed the 1,180 patients in **8 batches of 150 patients** (the
last batch has 130), in sorted file order.

This is valid because each Synthea patient bundle is self-contained: every reference points to a resource in the
same bundle. The only effect is on duplicate detection, which can't see copies of Practitioner and Organization
resources across batches.

Every patient was processed through the application's own ingestion path, the same parser and store as uploads.

## E1. FHIR validation accuracy

**Method.** In each batch, 25 resources per defect type were copied and mutated with one known defect. Each defect
type was injected and validated **in its own pass**, so one defect can't mask another. Ground truth comes from
construction: an injected record must be reported with the expected issue code and must count as invalid, and
every other record in the pass must stay valid. Malformed NDJSON was tested separately with 50 lines of each kind.

**Results.**
- **Injected defects:** all 3,000 (15 types × 200) were reported with the expected code and counted invalid.
- **False positives:** 0 of 7,903,695 clean record checks were flagged invalid (summed over the 15 passes).
- **Malformed NDJSON:** 50 of 50 truncated lines, 50 of 50 untyped objects, and 50 of 50 non-object lines were
  reported. Exactly the remaining 850 resources were read.
- **Baseline:** the unmodified Synthea data produced **0 errors**. Its 2,914 warnings are duplicates (E4) plus one
  out-of-scope note per resource type.

| Defect types (200 each) | Expected code |
| --- | --- |
| Status or gender outside the code set | `invalid-code` |
| Impossible date (2019-02-30); birth date in MM/DD/YYYY | `invalid-date` |
| Reference or CodeableConcept given as a string; value plus `dataAbsentReason` | `invalid-structure` |
| Non-numeric `valueQuantity.value` | `invalid-value` |
| Id containing a space | `invalid-id` |
| Misspelled resource type | `unknown-resource-type` |
| Subject pointing to a Practitioner | `invalid-reference` |
| Missing Observation status or Condition subject | `missing-required-field` |
| Missing Observation code | `missing-code` |
| Missing Observation value | `missing-value` |

**Interpretation.** The rules do what they were written to do, with no false alarms on 527,113 well-formed
resources. **This is not a measure of real-world accuracy.** The defects are the ones the rules target, and Synthea
data is unusually clean. Profile, terminology, and most FHIRPath checks aren't implemented (see LIMITATIONS.md).

## E2. PHI detection precision and recall

**Method.** The unit is a *location*: one element instance in one resource, such as
`Patient.address[0].postalCode`. Labels come from a written reference policy (`evaluation/phi_truth.py`), applied
without calling the detector. The policy is modelled on the identifier categories of the HIPAA Safe Harbor method.
It is a labelling yardstick only, not a compliance test.

| Labelled PHI | Labelled not PHI |
| --- | --- |
| Names | State and country |
| Street address, city, postal code | Gender, marital status, language |
| Latitude/longitude | Non-identifying extensions (race, ethnicity, birth sex, DALY/QALY) |
| Birth date with month or day (or a bare year for ages 90+) | |
| Date of death | |
| Telephone and e-mail | |
| Record and identifying numbers (MRN, SSN, driver's licence, passport) | |
| Name of a relative (mother's maiden name) | |
| Birth place (city) | |

- **Free text** (narratives and reference display text) is PHI only if it contains the patient's *full* name or
  another unique value (phone, identifier, street, postal code), matched as whole tokens.
- **Planted locations.** For each patient, a seeded generator also planted six controlled items: a narrative with
  the patient's name, a decoy narrative without one, free text with name and phone in `Observation.valueString`, a
  street address in `Condition.note`, the patient's name as `Condition.subject.display`, and a clinician's name as
  `Condition.asserter.display`.

**Results (302,269 labelled locations; 118,247 findings).**

| Scope | TP | FP | FN | Precision | Recall |
| --- | --- | --- | --- | --- | --- |
| **All locations** | 111,104 | 7,143 | 3,513 | **94.0%** | **96.9%** |
| Structured Patient fields | 15,071 | 1,180 | 1,180 | 92.7% | 92.7% |
| Reference display text | 94,853 | 0 | 0 | 100.0% | 100.0% |
| Narrative (`text.div`) | 1,180 | 5,963 | 0 | 16.5% | 100.0% |
| Free text (`valueString`, `note`) | 0 | 0 | 2,333 | n/a | **0.0%** |

Where the errors come from:
- **Structured false negatives (1,180):** every address latitude/longitude extension was missed. No rule covers it.
- **Structured false positives (1,180):** the state/country finding. The detector flags it at *low* severity, but
  the policy doesn't count a state as an identifier.
- **Narrative false positives (5,963):** the detector flags *every* narrative. Synthea's 1,180 Patient narratives
  and 3,603 CarePlan narratives contain no identifying text, and neither do the 1,180 planted decoys.
- **Free-text false negatives (2,333):** identifying text in `valueString` and `note` is never detected. This is by
  design: no NLP is used.
- **Everything else:** names, telecom, identifiers, street, city, postal code, dates, relatives, and Patient
  reference display text were found at 100%, with no false positives on 168,827 display texts of other parties or
  on 1,062 planted clinician-name decoys.
- **Precision by severity:** counting only high- and medium-severity findings, precision is 94.9%.
- **Speed:** the scan took 1.46 s for 527,113 resources.

**Interpretation.** The detector is reliable for the structured fields it targets. Its blind spots are exactly
where the design says they are: free text, and fields without a rule (geolocation). Flagging all narrative is a
deliberately conservative choice. It costs precision but guarantees narratives are reviewed (and the sanitizer
always removes them).

## E3. Data-quality defect detection

**Method.** As in E1, with 11 completeness and consistency defect types, 200 each, each in its own pass:
- missing Patient name, gender, or birth date; missing Condition code or onset; missing Observation effective date;
- future onset; abatement before onset; Observation before the patient's birth;
- unresolved subject reference; active status on a condition with an abatement date.

A combined pass measured how the scores respond.

**Results.**
- **Detection:** 2,200 of 2,200 defects were reported with the expected code.
- **False positives:** 0 of 5,796,043 clean record checks were newly flagged invalid.
- **Completeness accounting:** the missing-field count rose by exactly the number of injected missing fields in
  48 of 48 passes (1,200 total). This confirms that the "missing values" indicator and the completeness score are
  consistent by construction.
- **Score response (combined pass, mean over batches):** completeness 100.00% → 99.92%, validity
  100.00% → 99.94%, consistency 100.00% → 99.64%, uniqueness unchanged at 99.46%.

**Interpretation.** Each defect moves the dimension it belongs to, and the indicators are exactly consistent. The
size of the score changes reflects how few records were damaged (275 per batch of about 66,000), not the
sensitivity of the scores.

## E4. Duplicate detection

**Method.** For each batch, 10 new records per case were built from random existing ones and appended. Ground
truth comes from construction.

| Case | Truly a duplicate | Flagged |
| --- | --- | --- |
| Identical copy, same id | yes | 80 of 80 |
| Same id, changed value | yes | 80 of 80 (`conflicting-duplicate-id`) |
| Same content, new id | yes | 80 of 80 |
| Patient re-registered: new id and name, same identifiers | yes | 80 of 80 |
| **Same person re-registered with new identifiers** | yes | **0 of 80** |
| Observation with new id and value + 1 | no | 0 of 80 |
| Observation with new id and date one year earlier | no | 0 of 80 |
| Different person: new id, name, and identifiers | no | 0 of 80 |

- **All cases:** precision 100%, recall 80%.
- **Excluding the fuzzy case:** precision 100%, recall 100%.
- **The miss is by design:** a person re-registered with new identifiers can only be found by probabilistic record
  linkage, which isn't implemented.

**Flags in the unmodified data, all real:**
- **1,200 Practitioner and 1,200 Organization resources:** identical copies repeated across patient bundles. A
  merged dataset genuinely contains each one many times.
- **385 Observations and 1 Procedure:** byte-for-byte identical content (except the id) within the same patient
  record, an artifact of the Synthea output.
- **1 Patient:** flagged because two *different* synthetic patients share the same SSN value. That's a false
  positive with respect to "same person", but a data problem a reviewer should see.

## E5/E6. Processing time and throughput

**Batch mode (the full dataset, 8 batches).**
- **Ingest:** 41.8 s (parsing and the temporary store).
- **Processing:** 51.6 s for validation, quality, PHI scan, analytics, R, and persistence.
- **Total:** 93.4 s for 527,113 resources. That is **5,646 resources/s** end to end and **10,223 resources/s** for
  processing alone.

**Single process.** Each run is a fresh process; the table shows the median of 3 runs.

| Patients | Resources | End to end | Resources/s | Peak committed memory |
| --- | --- | --- | --- | --- |
| 50 | 17,395 | 3.2 s | 5,435 | 722 MB |
| 150 | 64,078 | 11.5 s | 5,592 | 1,139 MB |
| 300 | 119,424 | 21.4 s | 5,570 | 1,638 MB |
| 600 | 247,861 | 45.0 s | 5,504 | 2,781 MB |

- **Scaling:** throughput is flat and memory grows linearly, about 3.7 MB per additional Synthea patient.
- **Where the time goes:** at 600 patients, ingest (20.2 s), loading resources from SQLite (6.7 s), validation
  (6.0 s), and analytics (7.7 s). R took 2.2 s and the PHI scan 1.7 s.
- **1,180 patients in one process: not run.** The memory guard estimated 6.5 GB needed; 4.26 GB was free. By linear
  extrapolation it would need about 5 GB (an estimate, not a measurement).

**End-to-end through the browser.**
- **What was run:** the real Streamlit app, driven by headless Microsoft Edge. 150 Synthea patient files
  (165 MB, 64,078 resources) were uploaded through the file uploader, then *Process dataset* was clicked.
- **Timings (one run, measured from the browser):** upload and ingest took **6.2 s**. The dashboard was fully
  rendered **11.8 s** after the click (the pipeline itself took 6.8 s).
- **Errors:** none on the page or in the server log, across all eight dashboard sections.

## E7. Sanitization

Both configurations ran on all 527,113 resources.
- **Default:** pseudonymized identifiers and ids, state only, birth year, dates by month.
- **Strict:** identifiers, addresses, and birth/death dates removed; dates by year.

| Measure | Default | Strict |
| --- | --- | --- |
| Resources in / out | 527,113 / 527,113 | 527,113 / 527,113 |
| Validation errors before / after | 0 / 0 | 0 / 0 |
| Reference problems before / after | 0 / 0 | 0 / 0 |
| High-risk findings remaining | 0 | 0 |
| Output re-parsed by the app | 527,113 resources, 0 parse issues | not run |
| Time (sanitize + validate + re-scan) | 59.0 s | 55.7 s |

**Remaining findings, default settings (all intended):**
- 5,409 pseudonymized identifiers (low; linkage keys by design);
- 1,180 state values (low);
- 1,127 birth years and 180 death years (low);
- 53 birth years flagged *medium*: the patients aged 90+, whose birth year was grouped to "90 years before the
  reference date". The detector can't tell a grouped year from a real one.

**Original values searched for in each patient's sanitized resources** (whole-token match):

| Value type | Checked | Still present | Where |
| --- | --- | --- | --- |
| Name parts | 2,689 | 13 | Practitioner names only: clinicians who share a surname with their patient, not the patient's data |
| Telephone | 1,180 | 0 | |
| Identifier values | 4,229 | 0 | |
| Street | 1,180 | 0 | |
| **Postal code** | 893 | **231** | **Organization and Practitioner addresses**: the patient's clinic is in the patient's ZIP code |
| Full birth date | 1,180 | 0 | |

**Interpretation.** Sanitization removed or transformed every patient-identifying field it targets without breaking
validity or references. It does **not** touch other parties' data, so provider addresses remain an indirect location
signal for about a quarter of patients (231 of 893 with a postal code). That gap is documented, not fixed: provider
data isn't patient PHI, but in combination it narrows where a patient lives.

## E8. Analytical information preserved

**Method.** For the same valid, de-duplicated records, statistics from the raw data (exact birth dates, exact
dates, original ids) were compared with those from the pseudonymized analytical dataset (birth year, month,
pseudonymous keys).

| Measure | Result |
| --- | --- |
| Records (patients / conditions / observations) | 1,179 / 8,766 / 259,544 in both |
| Gender and state distributions | Identical |
| Condition prevalence (137 codes) | Identical (maximum difference 0.0000 percentage points) |
| Numeric observation series (104 code-and-unit series) | Identical n; maximum difference in mean and SD 0.000000 |
| Monthly counts of observations and condition onsets | Identical |
| Records linked to their patient | Identical (8,759 conditions; 259,426 observations) |
| Age group: birth year vs exact birth date | **98.98% agreement**; distribution total variation distance 0.51% |
| Information removed by design | 243 cities, 135 postal codes, and exact days (8,677 distinct observation days reduced to 796 months) |

Notes:
- **One patient excluded:** the second patient of the shared-SSN pair (E4) is excluded as a duplicate. That is why
  there are 1,179 patients, and why 7 conditions and 118 observations aren't linked in either dataset.
- **Ages:** deceased patients are aged at death in both the raw and the analytical data.
- **Misclassification:** age is computed from the birth year alone, so patients whose birthday hasn't come yet this
  year count one year too old. About 1% move up one age band.

**Interpretation.** For the descriptive statistics the dashboard reports, pseudonymization and generalization cost essentially
nothing except near age-band boundaries. Anything that needs exact dates, intervals, or sub-state geography can't
be done on the analytical dataset.

## Issues found and fixed during this evaluation

The evaluation and the engineering review found and fixed these genuine problems. Before/after figures marked *dev*
come from development runs during this phase, not from the final results files.

| Problem | Fix | Evidence |
| --- | --- | --- |
| One warning per out-of-scope resource buried real warnings and flooded the history database | One dataset-level note per resource type | *dev*: 17,596 warnings on 100 patients → 16 notes |
| The pipeline loaded the dataset twice and sanitized out-of-scope resources it then discarded | Load once; analytics sanitize in-scope resources only | *dev*, 300 patients: 22.1 s → 9.9 s; peak commit 2,514 MB → 1,654 MB |
| **Exact birth dates survived sanitization** in encounters, claims, immunizations, and observations dated on the day of birth (event dates were coarsened only in Condition and Observation, and kept by default) | Coarsen dates in every non-Patient resource; default changed to month | *dev*, 20 patients: 2 of 20 birth dates still present → 0. Final: 0 of 1,180 |
| **Grouping ages 90+ used today's date for patients who died young**, moving a birth year past the year of death | Age at death for deceased patients, in the sanitizer, the PHI detector, and the analytics | First full run: 1 new validation error after sanitization and 142 patients grouped → final: 0 errors, 53 grouped |
| The sanitization form opened on the first option of each setting, not the configured defaults | Defaults come from `SanitizationConfig` | Regression test |
| Deeply nested JSON crashed the parser with `RecursionError` | Rejected ("nested too deeply"), or the NDJSON line skipped | Regression tests |
| CSV downloads could carry spreadsheet formulas from uploaded data | Formula-like cells prefixed with `'` | Regression test |
| Uploaded file names were interpolated into Markdown (remote images, links) | Escaped | Regression test |
| JSON reports could contain the invalid tokens `NaN` and `Infinity` | Values cleaned; `allow_nan=False` | Regression test |
| The report cache key used an object id that can be reused, so a stale sanitized ZIP could be served | Keyed on the sanitization timestamp | Code review |
| Removing files used one SQL parameter per file (limit 999 on older SQLite) | Deletion decided in Python | Regression test with 1,200 files |
| A log message included the uploaded file name (Synthea file names are patient names) | Logs the SHA-256 instead | Regression test |
| The "Processed" tile truncated its timestamp | Time only; the date stays in the page caption | Browser screenshot |

Three flaws in the evaluation harness itself were found and fixed before the final run. Each would have
misreported results.
- **Interference:** defects injected together masked each other (for example, removing a birth date hid "before
  birth"). The first run showed 174 of 200; each type now runs in isolation.
- **Labels:** clinicians who share a surname with their patient made 50 practitioner display texts look like
  patient PHI. Labels now use full names.
- **Invalid ids:** injected invalid ids collided with each other.

## Threats to validity

- **Synthetic data.** Synthea output is clean and regular, and real exports contain error patterns not modelled
  here. Baseline results (0 errors) say nothing about real data.
- **Defects target the rules.** Injected defects are the kinds the validator checks, so high detection rates are
  expected and mainly show that the rules were implemented correctly and don't misfire. They don't show coverage of
  unknown problems.
- **Labels were defined by this project.** The PHI labels follow a written policy defined for this evaluation.
  Another policy (for example, treating state as identifying) would change precision. The planted free-text items
  are simple and template-based.
- **Batching.** Batching hides cross-batch duplicates of Practitioner and Organization resources. All other
  measures are unaffected because patient bundles are self-contained.
- **Performance was measured on one machine.** Other applications were running, so timings vary between runs
  (for example 3.2–4.1 s for the 50-patient runs). The browser timings come from a single run.

## Reproduce

```powershell
pip install -e ".[dev]"            # plus R 4.x on PATH or HDI_RSCRIPT for the R parts
python -m evaluation.run_evaluation
```

The command downloads and verifies the dataset (85 MB, into the git-ignored `evaluation/data/`), runs every
experiment with the fixed seed and reference date, and rewrites `evaluation/results/`.
- **Duration:** about 18 minutes on the evaluation machine.
- **Options:** `--help` lists them; `--patients N --batch-size M` gives a quick run.
- **Expected differences:** timings, memory, and which single-process sizes the memory guard allows depend on
  the machine. The accuracy, privacy, sanitization, and information results are deterministic and should be
  identical. The harness itself is tested in `tests/test_evaluation_harness.py`.
